# Synthetic data model

This document describes the synthetic Jira-like and Zephyr-like dataset used by the QA dashboard POC. All data is generated. None of it comes from a real Jira instance, a real client or a real person.

Status: draft for review (Phase 2). Volumes and value lists may change after review.

## Sources being simulated

The original Power BI dashboard used three kinds of source. The POC keeps the same split so that the dashboards can later be pointed at real sources one at a time.

| Source in Power BI | Simulated by | Files |
|---|---|---|
| Jira (issues) | Jira-like issues | `issues.json` |
| Zephyr (tests) | Zephyr Scale-like test cases, cycles and executions | `test_cases.json`, `test_cycles.json`, `test_executions.json` |
| Supporting datasets (Excel or SharePoint lists, assumed) | Reference and tracking tables | `teams.json`, `projects.json`, `users.json`, `coordinator_assignments.json`, `qa_reports.json` |

The nature of the supporting datasets is an assumption. Reporting timeliness and QA coordinator retention cannot come from Jira or Zephyr alone, so the POC models them as separate tables.

In the Streamlit POC, each file above is a table of the same name in the local SQLite database `data/qa_dashboard.sqlite`, generated by `qa_dashboard/data/generator.py` and checked by `qa_dashboard/data/validation.py`.

## Entity relationship overview

```
teams 1 ──< projects 1 ──< issues
  │             │   └────< test_cases 1 ──< test_executions >── 1 test_cycles
  │             │                 │                 │
  │             └────────────────────────────< test_cycles
  │                               │                 │
  │                     (covers) stories        (raises) bugs
  │
  ├──< users (QA members)
  ├──< coordinator_assignments >── users
  └──< qa_reports
```

Rules:

- A project belongs to exactly one QA team. Each team owns two projects.
- An issue, test case or test cycle belongs to one project. Its QA team is always the project's team.
- A test execution references one existing test case and one existing test cycle, and both belong to the same project.
- A test case can cover one story (requirement link). A failed execution can raise one or more bugs.
- An incident can be linked to the production bug that caused it.

## Reference period

| Setting | Value |
|---|---|
| History start | 2025-11-01 |
| Reference date ("today" for the dataset) | 2026-10-31 |
| Random seed | 42 |

The reference date is fixed rather than taken from the system clock. Statuses such as "overdue" therefore stay the same every time the data is regenerated.

| Status | Status category |

#### Due date rules

About 85% of bugs get a due date of created plus a target number of days by priority. The rest have no due date, as often happens in real Jira projects.

| Priority | Target days |
|---|---|
| Highest | 2 |
| High | 5 |
| Medium | 15 |
| Low | 30 |
| Lowest | 45 |

These targets are placeholders. If the Power BI dashboard used real SLA values, they replace these.

## Consistency rules checked by the generator

The validation script fails if any of these rules is broken.

1. Every foreign key points to an existing row (project, team, user, test case, cycle, story, bug).
2. An issue, test case, cycle or execution has the same team as its project.
3. `resolved` and `resolution` are set if and only if status_category is Done.
4. `created` is no later than `updated`, and `resolved` falls between `created` and the reference date.
5. A bug's reporter is a QA member and its assignee is a developer.
6. `executed_on` is set if and only if status is not Not Executed, and it falls within or close to the cycle dates (allowed slip: 7 days).
7. An execution's test case and cycle belong to the same project.
8. Automated executions only exist for test cases with `automated_since` on or before the execution date.
9. `failure_reason` is set only for Fail. `defect_keys` is set only for product defects, and the linked bugs are created on or after the execution.
10. An incident's linked issue is a PROD bug in the same project.
11. Coordinator assignments for a team do not overlap, and the assignee is a QA Coordinator.
12. No date is after the reference date.

POC note on rule 12: a bug's `due_date` (created plus target days) can fall after the reference date for bugs created near it. The Streamlit POC keeps these due dates and exempts `issues.due_date` from the check. To be confirmed.

## Realism rules

Random values are shaped to produce believable trends rather than flat noise.

- Bug creation peaks in the two weeks before each release and drops at weekends and over the Christmas period.
- About 70% of bugs are resolved. Older bugs are more likely to be closed than recent ones.
- Resolution time depends on priority. Highest bugs close in days, Low bugs in weeks.
- Projects with High criticality have more bugs and more production incidents.
- One team is deliberately weaker (lower pass rate, slower resolution, late reports) and one is stronger, so that comparisons show something.
- Automation coverage grows gradually over the 12 months, from about 25% to about 45% of active test cases.
- NRT cycles run before each release, with execution rates mostly between 85% and 100%.
- Two coordinator changes happen during the period, which gives the retention KPI something to show.

## API representation

The generator stores flat records. The mock API exposes them in two shapes:

- Jira-like raw endpoints return the Jira REST layout, for example `fields.status.name`, `fields.status.statusCategory.name` and `fields.priority.name`. This keeps the API close to what a real Jira connector would receive.
- Dashboard endpoints return flat rows and pre-computed KPIs. These are the shapes the Grafana panels use.

The Streamlit POC does not use the mock API. It reads the flat records directly from SQLite and computes KPIs in Python on every filter change. A future Jira or Zephyr connector only needs to produce the same flat tables.
